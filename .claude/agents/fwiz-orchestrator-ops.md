# Fwiz Orchestrator — Operations

This file holds full text for the orchestrator's system-hygiene rules: oracle policy, background-task discipline, cycle-completion checklist, artifact placement, retention. The core profile (`fwiz-orchestrator.md`) carries TL;DR versions of the most-frequently-applied items; this file is the canonical reference.

Sibling files: `fwiz-orchestrator.md` (core), `fwiz-orchestrator-protocols.md` (conditional decision protocols).

## Quality Bar (tiered oracle)

**Per-cycle gate (mandatory)**: `make test && make sanitize && make analyze-fast` (cppcheck — ~1-2 min). Every cycle. No exceptions.

**Periodic full oracle (user-triggered, static)**: `make analyze-full` (clang-tidy — **~10 s** post-2026-05-07 hang fix). The earlier "~1-2 h on this header-heavy codebase" claim was wrong: the tool was hanging indefinitely on `bugprone-exception-escape` (whole-call-graph noexcept analysis on inlined templates) for ~9 cycles / 1+ week. The 2026-05-07 bisection (`.fwiz-workflow/debug-analyze-full-hang.md`) excluded that check plus a defensive co-exclude (`bugprone-unchecked-optional-access`, LLVM #55530/#69298 known regression hang); wall-clock dropped to single-digit seconds. The user runs this whenever convenient — no longer "PC idle window" gate. The orchestrator's job is: (a) **track cycles-since-last-run** — at each cycle close, count `## NEW CYCLE` markers since the last `clang-tidy: green` commit annotation and surface in `next-priorities.md`; (b) **audit residuals when the user runs the batch** — read the log, grep findings (see "What to grep" below), diff against the last clang-tidy baseline, triage findings against the cumulative diff. There is **no hard-stop**, no 3-strike escalation.

**Periodic full oracle (user-triggered, runtime)**: `make valgrind` (memcheck — **~5-8 min** with `--track-origins=yes` on the 3330-test suite). Complementary to per-cycle `make sanitize` — ASan/UBSan are faster and stay in the per-cycle gate; valgrind catches certain uninitialized-read and heap-layout patterns ASan misses, and is compiler-portable. **Clean baseline established 2026-05-12**: 3330/3330 tests pass under valgrind with 0 errors, 0 leaks (the arena allocator design pays out here — `ExprArena::Scope` RAII pairs every allocation with a destructor-time free, so leak surface is essentially zero). Output captured to `/tmp/fwiz-valgrind.log`; printed only on failure. Orchestrator job: (a) **track cycles-since-last-run** parallel to clang-tidy tracking — surface in `next-priorities.md`; (b) **audit findings if `make valgrind` exits non-zero** — the captured log will contain the full valgrind error report at that point. Run recommendation cadence: after substantial allocator-pattern changes (`ExprArena` API edits, new arena-Scope sites, raw `new`/`delete` introduction), or before release. **Escalation rule** (parallel to clang-tidy): if `make valgrind` is "pending" for 3+ cycles with zero successful runs, escalate to debugger-agent diagnostic — but the bar for "pending" is higher than for clang-tidy because valgrind is only relevant when allocator surface has changed.

**Cross-cycle pattern escalation rule (added 2026-05-07)**: if a user-triggered tool is "pending" (recommended but not run, OR launched but never produced output) for **3+ consecutive cycles with zero successful runs**, do NOT keep recommending the tool — escalate to a debugger-agent diagnostic. The 9-cycle clang-tidy hang surfaced this miss: orchestrator kept writing "user runs `make analyze-full` during next idle window" to `next-priorities.md` for 9 cycles while every launch produced 0 bytes. The signal "9 launches, 0 completions" should have fired escalation at cycle 4, not cycle 9. Counting rule: a tool counts as "pending" for cycle N if cycle N's `next-priorities.md` recommends it AND the launch attempt produces no output AND the user does not explicitly defer it. When the threshold trips, the orchestrator opens a diagnostic micro-cycle (debugger agent + optionally researcher for tool-replacement survey) before the next forward-progress cycle.

**What to grep (both fast and full)**: exit code 0 only means the tool ran — NOT warning-free. MUST grep `warning:` / `error:` / `style:` / `performance:` in `src/*.h`, `src/*.cpp` and compare to previous baseline. Report delta (before, after, new). cppcheck emits `style:` / `performance:` severity prefixes for issues clang-tidy doesn't catch (constVariableReference, shadowFunction, constVariablePointer); grepping only `warning:` / `error:` silently misses them (Cycle B `--cse` baseline). Exit code alone is a reporting failure (baseline: `046bfec`).

**clang-tidy "N warnings generated" header is NOT the categorized-findings count.** clang-tidy prints a summary like `36 warnings generated.` at the end of its output even when zero user-visible warning lines were emitted. The `N warnings generated` count includes header-only diagnostics that the `-header-filter` excludes from the user-visible stream — they exist internally but never hit stdout. The authoritative count is the line count of `^.*: warning:` matches in the log body, NOT the summary header. Verify with `grep -cE '^[^:]+:[0-9]+:[0-9]+: warning:' <log>` and compare to baseline. Canonical: Cycle 7.5 post-fix run 2026-05-07 — `336 warnings generated` baseline → `36 warnings generated` post-fix, but BOTH had zero user-visible warning lines on the post-fix run (all 245 categorized findings cleared). Reading the header alone would have created a false "36 residuals" panic.

**Why this policy** (post-2026-05-07): clang-tidy on `src/main.cpp` walks ~10 k LOC of transitively-included headers but completes in ~10 s once the pathological check is excluded — header-heavy is not actually slow when no individual check is broken. The historical "1-2 h" claim was mis-attribution: the hang was a single-check pathology, not a structural cost of the codebase. Run cadence is therefore not bounded by tool cost — it's bounded by human cycle-close ergonomics and the marginal value of running on every micro-diff. Per-cycle running is feasible if desired; the user-triggered batch policy stays because the cppcheck per-cycle gate already catches most issues and clang-tidy's findings are rarely time-critical.

### Bridge task — when the user runs `make analyze-full`

Not a phase. Read the log, grep `warning:` / `error:` / `style:` / `performance:` in `src/*.h`, `src/*.cpp`, diff against the last clang-tidy baseline, triage findings against the cumulative diff (which files / lines have changed since the last green run), and either self-fix (mechanical, <5 LOC) or spawn a micro-cycle implementer per finding cluster.

### Historical context (no longer load-bearing)

The retired "Oracle-less cycle protocol" + 3-strike rule modeled the case where every cycle was **expected** to run clang-tidy and deferrals were exceptions. Three consecutive deferrals (T1 2026-04-28, T2+T3 attempts 2026-04-30 and 2026-05-02) — each individually sound under contention — were attributed to clang-tidy being structurally a 1-2 h task on a header-heavy codebase. **That attribution was wrong**: the 2026-05-07 bisection identified `bugprone-exception-escape` as a single hanging check, not a structural cost. The "1-2 h" wall-clock the policy assumed never actually happened — every observed run hit infinite-hang or got killed. The 3-strike rule's removal stands (it modeled an exception case that didn't exist), but the new policy is now grounded in the real ~10 s wall-clock and a different lesson: **run-cadence policy should be derived from measured wall-clock, not assumed wall-clock**. Future "this oracle is too expensive to gate" claims should require a successful timed run as evidence.

## Background Task Discipline

**Two-question pre-flight before EVERY backgrounded Bash call** (also stated in core; full details below cover the two recurring class-2 silent-success bugs):

1. **"Does my command body contain `&`, `nohup`, `( ... ) &`, or `cmd; touch sentinel &`?"** If yes AND you are about to set `run_in_background: true`, STOP — that is the double-background bug (rule #5). Pick exactly ONE backgrounding mechanism. If using `run_in_background: true`, the command must be foreground (no inner `&`).
2. **"Am I about to write `pgrep -f <token>` to check a process?"** If yes, STOP — `pgrep -f` is structurally banned for orchestrator-typed checks (rule #4); use sentinel file or `ps -ef`-with-shell-filter.

Both rules existed before recurrence (G1/G3 cycle 2026-04-24, provenance-plumbing cycle 2026-04-26 for #5; three escalating cycles for #4). The pre-flight banner is intended to fire BEFORE the typing reflex; the rule bodies below are the structural detail.

Wait for the completion notification on `run_in_background`. Do NOT poll partial logs, duplicate long tasks, or misread stale mtimes as current output.

1. **Tag every background task** with task-id, log path, launch timestamp. Before reading any `/tmp/fwiz-*.log`, check mtime vs launch timestamp — if mtime < launch, it's stale.
2. **Never start a duplicate long task** (make sanitize, make analyze) while another runs. The reliable check is a sentinel file (`[ -f /tmp/fwiz-analyze.running ]` — wrapper writes on launch, removes on exit) or `ps -ef | grep -E '<binaries>' | grep -v grep | grep -v zsh | grep -v bash` (the explicit shell-filter pattern; works even when the orchestrator's argv contains the binary name). Do NOT use `pgrep -f <token>` — anchored or not. Even a "unique tag" (`pgrep -f "fwiz_running_unique_tag_optC"`) self-matches because the moment the orchestrator types the tag into a Bash command, the tag becomes part of the orchestrator's own argv. Successive cycles (Cycle B 2026-04-25, Option C 2026-04-26) re-discovered this with anchored / unique-tag variants. The structural fix is: there is no `pgrep -f` form that the orchestrator can write that won't appear in its own argv. Use sentinel-file or `ps -ef`-with-shell-filter.
3. **Hung-task threshold**: 2x expected duration for *silent* hangs (no output). `make analyze-full` post-fix takes ~10 s on a clean PC; not hung before ~2 min silence. `make analyze-fast` takes ~1-2 min; not hung before ~5 min. (Earlier policy used "~1-2 h baseline / 3-6 h thresholds" for analyze-full; that came from the never-completing pre-2026-05-07 hang state and was a fiction.) **Oracle-contention escape (analyze-full only)**: if `analyze-full` etime exceeds 30× expected (~5 min) AND `ps -o %cpu,comm ax | sort -rn -k1 | head -5` shows a non-fwiz process consuming > 200% CPU (system contention, not analyze itself), surface to the user: "analyze-full running 30× expected under {process} contention — kill and retry later? (yes/no)". Do not silently wait. Canonical miss: T1 cleanup cycle 2026-04-28 — clang-tidy ran 18.5 h under llama-server at 546% CPU before the user proactively offered batch-defer; subsequent 2026-05-07 investigation revealed the 18.5 h was mostly the `bugprone-exception-escape` hang, not contention.
4. **`pgrep -f` self-match is structural — `pgrep -f` is banned for orchestrator-written process checks.** Any string the orchestrator types into a Bash command becomes part of that command's argv; `pgrep -f <token>` therefore matches itself. This fires identically in (a) wait-loops (`while pgrep -f <name>; do sleep N; done` runs forever after task completes), (b) pre-launch existence checks (`pgrep -f clang-tidy` produces false-positive WARN), and (c) "unique-tag" anchored variants (`pgrep -f "unique_tag_optC"` — the tag is now in the orchestrator's own argv too). Three escalating cycles (derive-ordering wait-loop `2026-04-20`, Tier 1.x pre-launch `2026-04-25`, Option C unique-tag `2026-04-26`) confirm there is no `pgrep -f` form that survives. Use exactly ONE of: (a) `run_in_background: true` on the task itself (harness owns the wait, no watcher needed — strongly preferred); (b) PID captured at launch + `kill -0 $PID` to test liveness; (c) sentinel file written on launch / removed on exit + `[ -f /tmp/fwiz-analyze.running ]`; (d) `ps -ef | grep -E '<binary>' | grep -v grep | grep -v zsh | grep -v bash` (the wrapper-shell exclusion handles cases where the orchestrator's own command line is a `zsh -c ...`).
5. **Never double-background**: do NOT wrap `run_in_background: true` around a Bash command whose body itself contains `&` (or `nohup ... &`, or `( ... ) &`, or `cmd; touch sentinel &`). The harness's completion notification fires when the OUTER shell exits — and the outer shell exits as soon as it backgrounds the inner subshell, regardless of whether the long-running task has finished. Pick exactly ONE backgrounding mechanism: either (a) `run_in_background: true` on a foreground command (`make analyze 2>&1 | tee /tmp/log; touch /tmp/done`) — the harness owns the wait — or (b) a foreground shell with `nohup cmd &` and orchestrator polls a sentinel file via Bash with NO `run_in_background`. Never both. Canonical miss: G1/G3 simplifier-gap cycle 2026-04-24T10:35 — `make analyze` launched as `run_in_background: true` on a command containing `& touch sentinel`; harness fired completion ~immediately while clang-tidy was still running; orchestrator caught it via `pgrep` only because the log was suspiciously short. Recovery cost was zero (sentinel pattern already in place) but the near-miss is a class-2 bug (silent-success looks identical to real-success).

### Silent-run watchdog for `make analyze-full`

A clang-tidy run that produces zero output progress for ≥ 30× expected wall-clock (~5 min, given the ~10 s post-fix baseline) is **suspect**, not just slow — clang-tidy emits per-TU progress under contention, so total silence with zero log growth means the wrapper script's output-redirection is broken, the process is stuck on a single check, or a check has hit a pathological codepath. At the 30× silent mark, kill and re-launch with explicit per-check timing (run each top-level family separately under `timeout 60`) before assuming "still running." If repeated bisection finds a new hanging check, treat it as a fresh diagnostic micro-cycle (debugger agent), exclude the check in the Makefile with a rationale comment, and update the post-fix baseline number in this file. Canonical: 2026-05-07 — `bugprone-exception-escape` hung indefinitely across 9 cycles producing zero output; the cross-cycle pattern (9 launches, 0 completions) was the first signal that something was structurally broken. The single-instance watchdog above catches per-launch hangs; the cross-cycle escalation rule (see Quality Bar) catches multi-launch patterns.

### Duplicate-launch check for cppcheck (rare, but fast)

`ps -ef | grep -E 'cppcheck' | grep -v grep | grep -v zsh | grep -v bash`. Do NOT use `pgrep -f <token>` (rule #4 above).

## Cycle-Completion Checklist

Before declaring a cycle complete:

1. **No in-flight background tasks**: `ps aux | grep -E 'clang-tidy|cppcheck|make|fwiz'` — zero processes other than orchestrator.
1b. **Stray write-path-artifact sweep**: `ls src/.fwiz-workflow/ design-proposal.md src/design-proposal.md 2>&1`. Any hit is a misrouted agent write (relative-path-resolves-against-`src/`, or a `WRITE-PATH-VIOLATION:` sentinel written-to-file) — `rm` it before close and note in the cycle's meta-review process notes. The orchestrator already cleans these reactively after each incident; this checklist step makes the end-of-cycle sweep explicit so a stray that survived mid-cycle cleanup (e.g. created by a later spawn) doesn't persist into the next cycle. Canonical: gen-6 cycle 1 (2026-06-22) — 5 write-path incidents; strays at `src/.fwiz-workflow/design-proposal.md` and repo-root `design-proposal.md` recurred across planner + multiple implementer spawns. Profile fixes (absolute-path mandate + sentinel-to-text hardening in planner.md/implementer.md) are the source-side prevention; this sweep is the belt-and-suspenders catch.
2. **All logs final-state**: for each `/tmp/fwiz-*.log` cited in review-notes.md, mtime > last source-file mtime.
3. **Per-cycle residual audit (cppcheck)**: grep `warning:` / `error:` / `style:` / `performance:` in `/tmp/fwiz-analyze-fast.log` (or wherever `make analyze-fast` was teed) vs. cycle-start baseline. If delta non-zero OR any flag in an implementer-touched file/line, do NOT close — spawn a residual-fix pass (self-fix if trivial, implementer if not). cppcheck is the per-cycle oracle; grep is not.
4. **clang-tidy run tracking** — the per-cycle gate is cppcheck only; clang-tidy is user-triggered. Cycles-since-last-run is informational, not a debt counter (the tool runs in ~10 s post-fix; running per-cycle is feasible if desired).
   - At each cycle close, compute `cycles_since_clang_tidy`: count of `## NEW CYCLE` markers in `orchestrator-log.md` (active + archived) since the last commit annotated `clang-tidy: green` (or, if none yet, since the last green baseline noted in `next-priorities.md`).
   - Compute `cumulative_diff_lines`: `git diff --shortstat <last-green-commit>..HEAD` line count.
   - Append to `next-priorities.md` under a "## clang-tidy run tracking" heading: "{N} cycles since last run; cumulative diff {M} lines."
   - **Cross-cycle escalation rule**: if `cycles_since_clang_tidy >= 3` AND every prior recommendation produced zero successful runs, do NOT keep recommending the tool — escalate to a debugger-agent diagnostic. See Quality Bar §Cross-cycle pattern escalation rule.
   - When the batch runs and is clean (zero categorized findings), append `clang-tidy: green` to the cycle-close commit message; this resets the counter. If the batch surfaces findings, triage on the cumulative diff (which files / lines have changed since the last green); fix per-finding (self-fix mechanical, micro-cycle architectural).
5. **Artifact retention** — see §Artifact retention below.
6. **Workflow-metrics ledger append (anti-drift, mandatory at every cycle close)**: run `tools/metrics-append.sh CYCLE "<slug> — <one-line outcome>"`. This bumps the cumulative counter (firing the compact-pass %3 trigger when it lands on a multiple of 3) AND appends a dated per-cycle stub. The append is procedure, not prose — the ledger drifted ~24 cycles (froze at counter=21, 2026-05-09 → re-anchored to 45, 2026-06-21) precisely because this was a buried prose instruction with no checklist step or helper. Records-of-record for per-cycle *detail* are the orchestrator-log §Strategic Side Effects log + archived snapshots + meta-review reports; `workflow-metrics.md` carries only the counter + the most-recent quantitative table + file-size baselines for the compact pass. The meta-reviewer fills the stub's quantitative table at the next compact pass (do NOT block cycle close on it).

## Artifact placement — gitignored `.fwiz-workflow/` vs committed `docs/`

Where an artifact lives is determined by its lifecycle, not the phase that created it.

- **`.fwiz-workflow/` (gitignored)**: per-cycle working artifacts consumed within the cycle and by the immediate-next cycle's RESEARCH phase — `research-brief.md`, `design-proposal.md`, `implementation-log.md`, `review-notes.md`, `next-priorities.md`, `orchestrator-log.md`, `meta-review*.md`, `workflow-metrics.md`, per-cycle scratch diagnostics. The orchestrator may rotate these (suffix-rename at next-cycle start) but the directory itself is disposable; if cleared, the cycle can still reconstruct from commits.
- **`docs/` (committed)**: user-facing reference docs (`Language.md`, `Solver.md`, `Developer.md`, etc.) — Title-Case at top level.
- **`docs/research/` (committed)**: long-lived research anchors referenced from committed sources (`docs/*.md`, `CLAUDE.md`, inline code comments, commit messages). Lowercase-with-hyphens (`docs/research/category-c-investigation.md`, `docs/research/provenance-plumbing.md`). Criterion: if two or more committed docs reference the artifact, OR if any cycle beyond the immediate-next expects to consume it, OR if a commit message points to it, it belongs here.

Rule of thumb when authoring an investigation or research-anchor artifact mid-cycle: if you find yourself adding a reference to it from `docs/Future.md`, `docs/Known-Issues.md`, `docs/Developer.md`, or `CLAUDE.md`, place the artifact in `docs/research/` from the start. Avoids the post-hoc move that the reviewer catches. Canonical miss: P1-tautology cycle — `category-c-investigation.md` was first written to `.fwiz-workflow/`, referenced from `docs/Future.md #32` and `docs/Known-Issues.md #7`; reviewer flagged the discoverability risk; orchestrator moved it to `docs/`, then to `docs/research/` (2026-04-26) once a second research anchor (provenance-plumbing) made the subdirectory worth establishing.

## Artifact retention

Count suffixed artifacts in `.fwiz-workflow/` (`research-*.md`, `design-*.md`, `implementation-log-*.md`, `review-notes-*.md`, `next-priorities-*.md`, `meta-review-*.md`). If > 15, archive the oldest cycle into `.fwiz-workflow/archive/{cycle-name}/`, keeping only the meta-review at top level.

`orchestrator-log.md` retention: cumulative by default, but rotate when the file exceeds **~1500 lines or ~150 KB**. Rotation procedure: at end of cycle, move all cycle-closed entries (everything strictly before the most recent `## NEW CYCLE` or `### [...] CYCLE START` marker) to `archive/orchestrator-log-thru-{YYYY-MM-DD}.md`; keep the active cycle's entries in `orchestrator-log.md`. Rationale: the file is read in full by every meta-review and consumes ~30k tokens at 1500 lines — beyond that it dominates initial context cost. Option C cycle 2026-04-26 first hit this: file was 1192 lines / 147 KB at cycle start; Day 2 entries weren't logged at all, suggesting the orchestrator silently avoided the cumulative-write path under context pressure.
